# network-manager

NetworkManager в образе — чтобы Wi-Fi, объявленный в манифесте устройства,
на этом устройстве действительно поднялся.

## Зачем

`bs device write` при наличии секции `wifi` у интерфейса генерирует
`network-config` с `renderer: NetworkManager`: systemd-networkd Wi-Fi
не поддерживает вовсе (`docs/guides/device.md`, раздел «WiFi интерфейсы»).

Если NetworkManager в образе нет, cloud-init разложить профиль **некуда**,
и устройство приходит без сети. Отказ тихий: карта записалась, система
загрузилась, в журнале записи ошибок нет — новость приходит, когда
устройство уже в поле и по SSH до него не достучаться.

**Основной случай применения — «уже стоит».** Замерено в собранном образе
Raspberry Pi OS (2026-09-03): `network-manager`, `wpasupplicant`
и `firmware-brcm80211` там есть, юнит включён. Расширение это опознаёт,
говорит об этом и **не делает ничего** — ни `apt-get update`, ни установки.
Оно нужно для образов, где NetworkManager нет: собственные сборки Debian,
урезанные cloud-образы, минимальные netinst.

## Подключение

```vmfile
EXTENSION network-manager
```

Параметров нет.

Прежняя запись продолжает работать:

```vmfile
COPY_IN <чекаут>/extensions/debian/network-manager:/opt/vmsetup/
RUN_COMMAND chmod +x /opt/vmsetup/network-manager/*.sh
RUN_COMMAND /opt/vmsetup/network-manager/install.sh
```

`<чекаут>` — путь до чекаута этого репозитория **относительно каталога
VMFILE**; в примерах основного репозитория это `../../../../bisquite-extensions`,
и глубина зависит от того, насколько глубоко лежит сам VMFILE.

## Что делает

**Сборка** (`install.sh`)

- отказывается работать не на `debian`/`ubuntu` — по `ID` из
  `/etc/os-release`;
- смотрит, что уже стоит: `network-manager` и `wpasupplicant`;
- если оба на месте и юнит включён — сообщает и выходит, apt не трогая;
- иначе ставит недостающее и проверяет, что `NetworkManager.service`
  действительно включён;
- предупреждает, если в образе включён ещё и `systemd-networkd`;
- сообщает, нашлась ли в `/lib/firmware` прошивка Wi-Fi.

Первой загрузки у расширения нет: конфигурацию сети пишет cloud-init,
донастраивать нечего.

**`wpasupplicant` объявлен явно**, а не оставлен на `Recommends` пакета
`network-manager`: образы собирают и с `--no-install-recommends`, и тогда
ассоциация с точкой доступа отваливается уже на устройстве. Та же правка
и по той же причине сделана у расширения `x11vnc` (`xauth`, `x11-utils`).

## Прошивку не ставим

Прошивка Wi-Fi зависит от чипа: `firmware-brcm80211` для Raspberry Pi,
`firmware-iwlwifi` для Intel, дальше — Realtek, MediaTek, Atheros.
Расширение **не ставит ничего из этого**, и вот почему выбор нельзя сделать
за оператора:

1. **Осей две, а не одна.** Расширение `docker` ветвится по признаку железа
   (`/boot/firmware/cmdline.txt`, `/etc/nv_tegra_release`) — и этого хватает,
   потому что имена пакетов Docker на всех целях одинаковы. Здесь — нет:
   на Debian прошивки разложены по отдельным `firmware-*` в компоненте
   `non-free-firmware`, а на Ubuntu таких пакетов **не существует вовсе**,
   всё лежит в монолитном `linux-firmware`. Выбрать пакет — значит завести
   таблицу «железо × дистрибутив», а объявленная таблица в этом проекте
   отвергнутая ось: она устаревает молча.
2. **Признака железа в образе может не быть.** Pi-образ себя выдаёт
   (`/boot/firmware/cmdline.txt`), а обычный amd64-образ — нет: он поедет
   в любой ноутбук, и чип Wi-Fi станет известен только там. Угадывать
   значило бы тащить в образ прошивки на все случаи.
3. **Там, где ответ известен, он уже применён.** В Raspberry Pi OS
   `firmware-brcm80211` стоит из коробки — ставить нечего.

Что расширение делает вместо этого: смотрит `/lib/firmware` на признаки
известных чипов (`brcm`, `iwlwifi-*.ucode`, `rtlwifi`, `mediatek`, `ath10k`,
`ath11k`) и, не найдя ни одного, **предупреждает вслух** с именами пакетов
для обоих семейств. Нужную прошивку добавляйте слоем `INSTALL` **до**
этого расширения:

```vmfile
INSTALL firmware-brcm80211
EXTENSION network-manager
```

На Debian компонент `non-free-firmware` при этом должен быть подключён
в `sources.list` образа — на официальных образах Debian 12+ он подключён.

## Отказы

| Когда | Что делает |
|---|---|
| `ID` не `debian` и не `ubuntu` | отказ, код 1 |
| пакета нет в репозиториях образа | отказ с указанием проверить `sources.list` |
| пакеты встали, а юнит не включился | отказ, код 1 — тихо отдавать образ без сети хуже |
| прошивки Wi-Fi в образе нет | **предупреждение**, не отказ |

Последняя строка — граница между «расширение не сделало свою работу»
и «оператор не сказал, какое у него железо». Прошивка нужна не всем:
на устройстве без Wi-Fi NetworkManager осмыслен и без неё.

## Ограничения

**`systemd-networkd` не выключается.** Если в образе включены оба менеджера,
расширение говорит об этом предупреждением и оставляет как есть: выключить
networkd значило бы переписать сетевой стек чужого образа за его автора.
Разбирайтесь на месте — cloud-init при наличии Wi-Fi кладёт профили
NetworkManager, а Ethernet может остаться за networkd.

**Ничего не настраивает.** Ни одного профиля соединения расширение
не создаёт: SSID и пароль приходят из манифеста устройства через cloud-init.
Расширение отвечает только за то, чтобы было **чем** их применить.

**`phase: build`** — значит, архитектуры хоста и образа обязаны совпасть:
libguestfs не выполняет код в госте чужой архитектуры. Собрать arm64-образ
с этим расширением на amd64-хосте нельзя, и отказ приходит до сборки.

## Проверка

На собранном образе:

```console
$ virt-ls -a образ.qcow2 /etc/systemd/system/multi-user.target.wants/ | grep NetworkManager
$ virt-cat -a образ.qcow2 /var/lib/dpkg/status | grep -A1 '^Package: network-manager$'
```

На устройстве после первой загрузки:

```console
$ systemctl is-active NetworkManager
$ nmcli device status
$ nmcli connection show
$ journalctl -u NetworkManager -b | head -50
```

Wi-Fi виден как `disconnected`, а не `unavailable` — прошивка загрузилась.
`unavailable` при наличии адаптера почти всегда значит именно её отсутствие;
смотрите `dmesg | grep -i firmware`.
