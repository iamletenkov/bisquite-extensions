# vino-vnc

Удалённый рабочий стол по VNC штатным сервером GNOME — `vino`.

> **С 3.0.0 — раскладка 2.** Каталог расширения в госте — `/opt/bisquite/vino-vnc/`
> (был `/opt/vmsetup/vino-vnc/`); `ExecStart` юнита первой загрузки смотрит туда же, `lib/get_cloud_user.sh` —
> ссылкой на общий код источника, а не копией.
> Нужен bisquite с поддержкой `layout: 2`.

> **С 4.0.0 — библиотека настроек.** `/etc/bisquite/vino/config` — домен
> `vino` библиотеки `bisquite-conf` (схема `knobs`): `configure.sh` его больше
> **не исполняет** (`source`), установка не переписывает, `VINO_LISTEN` —
> только `localhost` или `all`, пароль ставится
> `bisquite-conf set vino VINO_PASSWORD=-`.

**С 2.0.0 файл параметров — `/etc/bisquite/vino/config`** (был `/etc/default/bisquite-vino`).
Прежний путь не читается; если файл по нему остался в базовом образе,
установка его удаляет.

## Зачем отдельное расширение, а не режим `x11vnc`

Общего кода почти нет, и это видно по устройству обоих:

| | `x11vnc` | `vino-vnc` |
|---|---|---|
| Кто запускает | системный юнит `x11vnc@<user>.service` | автозапуск XDG внутри сессии |
| Как находит дисплей | обёртка ищет X authority в рантайме | никак: он уже внутри сессии |
| Как настраивается | аргументы командной строки в обёртке | `gsettings` в dconf пользователя |
| Что ломается | путь к authority | отсутствие сессии |

Ни обёртки, ни authority, ни системного юнита у vino не бывает: он часть
GNOME и живёт внутри пользовательской сессии. Свести их в одно расширение
значило бы написать два непересекающихся скрипта под одним именем.

Зачем тогда второй сервер вообще: `vino` — то, что на GNOME-плате уже есть
в репозитории и что настраивает штатная панель «Общий доступ к рабочему
столу». Замер на Jetson Nano (2026-09-03) показал рабочую конфигурацию
именно через него.

## Манифест

| Поле | Значение |
|---|---|
| `phase` | `[build, firstboot]` |
| `provides` | `remote-desktop` |
| `requires` | `x11-server`, `display-manager` |
| `conflicts` | — (разбор ниже, «Соседство с x11vnc») |

`build` — `install.sh` ставит `vino` и пишет параметры; `firstboot` —
`configure.sh` применяет `gsettings` и кладёт автозапуск. Граница проходит
по природе задачи: `gsettings` пишет в dconf **конкретного** пользователя,
а его создаёт cloud-init уже на устройстве.

## Подключение

```vmfile
EXTENSION gnome
EXTENSION vino-vnc
```

Десктоп идёт **до** — порядок слоёв и есть то единственное, чем сегодня
держится `requires`.

`EXTENSION yq` этому расширению **не обязателен**, в отличие от `x11vnc`:
`configure.sh` не требует `yq` сам, а `lib/get_cloud_user.sh` без него переходит
на запасной путь — первую обычную учётку с uid 1000–65533 и домашним
каталогом. На образе с единственным пользователем это тот же ответ; там, где
учёток несколько, ставьте `yq` выше и получите именно пользователя из seed.

Ручной формы через `COPY_IN` больше нет: сборка кладёт каталог в
`/opt/bisquite/vino-vnc/` и ставит рядом ссылку `lib` на общий код источника,
а это делает только `EXTENSION` (раскладка 2, см. `docs/extensions.md`).

## Параметры

Задаются переменными окружения — в `EXTENSION` они пишутся `КЛЮЧ=ЗНАЧЕНИЕ`
и уезжают в `install.sh` как есть:

```vmfile
EXTENSION vino-vnc VINO_PORT=5901 VINO_PASSWORD=секрет
```

| Переменная | Умолчание | Что делает |
|---|---|---|
| `VINO_PORT` | `5900` | порт RFB; допустимо 5000–50000 |
| `VINO_LISTEN` | `localhost` | `localhost` — только петля (`network-interface='lo'`), любое другое значение — все интерфейсы |
| `VINO_PASSWORD` | пусто | пароль; без него `authentication-methods=['none']` |
| `VINO_ENCRYPTION` | `false` | значение ключа `require-encryption` |

Значение с пробелами берётся в кавычки — аргумент разбирается `shlex`,
и кавычки снимаются до попадания в окружение:

```vmfile
EXTENSION vino-vnc VINO_PASSWORD="two words"
```

`install.sh` отдаёт `VINO_PORT`, `VINO_LISTEN` и `VINO_ENCRYPTION` библиотеке
`bisquite-conf`: она проверяет их по схеме `knobs` и пишет в
`/etc/bisquite/vino/config`; `configure.sh` читает оттуда. Пароль туда
**не пишется**: это ключ `secret:hook`, и хук `knobs.secret` кладёт base64
(ключ `vnc-password` схемы `org.gnome.Vino` хранит пароль в base64) в
отдельный файл `/etc/vino/vnc-password.b64` с правами `0600`, а в файл
окружения — только путь (`VINO_PASSWORD_FILE`). В журнал не печатается ни
пароль, ни его base64.

Оговорка, важная при правке на живой машине: `/etc/bisquite/vino/config`
здесь **не `EnvironmentFile` какого-то юнита**, как у `x11vnc`. Его читает
`configure.sh` (библиотекой, не `source`) и переносит значения
в dconf пользователя. Настоящий источник правды для работающего сервера —
dconf, а файл параметров — то, из чего он заполняется.

**Диапазон портов взят из схемы**, а не выдуман: описание ключа
`alternative-port` говорит «Valid values are in the range of 5000 to 50000».
Значение вне диапазона — отказ на сборке, потому что vino просто не применил
бы его, и это выглядело бы как «порт закрыт» уже на плате.

**Умолчание `localhost`** — то же решение, что у `x11vnc`, и по той же
причине: compose-примеры ставят `firewall: false`, и сервер на всех
интерфейсах без пароля означал бы открытый рабочий стол из одной строки
VMFILE, которую никто не писал специально. Доступ — SSH-туннелем:

```bash
ssh -L 5900:localhost:5900 пользователь@адрес
```

Открыть наружу можно, но это придётся написать явно, и расширение скажет
в журнал, чем это кончится: **любой в этой сети получит рабочий стол
с правами вошедшего пользователя**. Без `VINO_ENCRYPTION=true` он вдобавок
увидит нажатия клавиш открытым текстом.

**Про `VINO_ENCRYPTION=false` по умолчанию.** Схема ставит `true`, и её
описание объясняет, зачем: «It is highly recommended that you use a client
which supports encryption **unless the intervening network is trusted**».
С умолчанием `localhost` промежуточной сети нет вовсе — трафик не покидает
машину, а туннель шифрует SSH. Замеренная рабочая конфигурация на Jetson
тоже `false`. Выставляете `VINO_LISTEN` наружу — ставьте и
`VINO_ENCRYPTION=true`, но проверьте, что ваш VNC-клиент умеет шифрование
vino: умеют не все.

Пароль длиннее восьми символов расширение примет и предупредит:
аутентификация VNC (RFB, тип 2) кладёт в ключ DES ровно восемь байт,
остальное отбрасывается.

## Параметры времени выполнения

Пересобирать образ, чтобы поменять порт или открыть сервер в сеть, не нужно.
Цепочка та же, что на первой загрузке: файл параметров → `configure.sh` →
dconf пользователя.

```console
$ bisquite-conf show vino
```

Переключить прослушивание с петли на все интерфейсы:

```bash
# 1. пароль — со stdin; хук кладёт base64 в /etc/vino/vnc-password.b64 (0600)
echo 'пароль' | sudo bisquite-conf set vino VINO_PASSWORD=-

# 2. адрес; хук ставит в очередь configure-vino-vnc.service — перенос в dconf
sudo bisquite-conf set vino VINO_LISTEN=all
sudo journalctl -u configure-vino-vnc -b | tail -20   # видно каждый выставленный ключ

# 3. поднять сервер с новыми ключами: он читает их при старте
#    надёжный путь — перелогиниться в сессию; без монитора —
sudo systemctl restart display-manager.service        # ЗАКРОЕТ текущую сессию

# 4. проверить
ss -ltnp | grep 5900
```

Вернуть обратно — то же самое со значением `localhost`. Перенос в dconf (хук
второго шага) обязателен: правка файла сама по себе не меняет ничего, потому
что сервер читает dconf, а не файл; во время загрузки хук не зовётся, и
перенос делает `configure-vino-vnc.service` при своём старте. Третий шаг —
потому что `network-interface` и порт `vino-server` берёт при запуске; правка dconf в уже работающей сессии на слушающий сокет
не переносится.

Тот же эффект даёт прямая правка dconf от имени пользователя, если
`configure.sh` рядом нет:

```bash
sudo -u <пользователь> dbus-run-session --   gsettings set org.gnome.Vino network-interface ''    # '' = все, 'lo' = петля
```

### Что именно произойдёт при `VINO_LISTEN=all`

- **рабочий стол становится доступен всем, кто дотянулся до порта** — уже
  открытой сессии, с правами вошедшего пользователя;
- **без `VINO_ENCRYPTION=true` трафик не шифруется**: нажатия клавиш,
  а значит и пароль `sudo`, идут по сети открытым текстом;
- **пароль VNC слаб по устройству протокола** — восемь байт в ключе DES
  (см. выше), перебор дёшев; без пароля
  `authentication-methods=['none']`, то есть аутентификации нет вовсе;
- **подтверждения подключения не будет**: `prompt-enabled=false` выставлен
  намеренно, иначе на безголовой плате не подключился бы никто;
- **compose-примеры ставят `firewall: false`** — экрана перед портом может
  не быть вовсе.

Штатный путь — оставить `localhost` и ходить SSH-туннелем: шифрование
и аутентификацию тогда даёт SSH.

## Что делает

- **Сборка** (`install.sh`) — проверяет и пишет параметры библиотекой
  `bisquite-conf` (`/etc/bisquite/vino/config` и, если задан, файл пароля —
  хуком), ставит `vino`, `libglib2.0-bin` и `dbus`, включает
  `configure-vino-vnc.service`.
- **Первая загрузка** (`configure.sh`) — резолвит пользователя cloud-init,
  применяет `gsettings` в его dconf и кладёт автозапуск
  в `~/.config/autostart/vino-server.desktop`.

Применяемые ключи `org.gnome.Vino`:

| Ключ | Значение | Почему |
|---|---|---|
| `prompt-enabled` | `false` | на безголовой плате подтверждать подключение некому; с `true` не подключится никто, а сервер при этом выглядит рабочим |
| `require-encryption` | из `VINO_ENCRYPTION` | |
| `authentication-methods` | `['vnc']` или `['none']` | зависит от того, задан ли пароль |
| `vnc-password` | base64 пароля | формат задан описанием ключа |
| `network-interface` | `'lo'` или `''` | пустая строка = все интерфейсы (описание ключа) |
| `alternative-port` / `use-alternative-port` | из `VINO_PORT` | 5900 — умолчание самого vino, ради него второй ключ не включается |

### Почему настройка на первой загрузке, а не на сборке

`gsettings` пишет в dconf **конкретного пользователя**
(`~/.config/dconf/user`), а автозапуск — в его `~/.config/autostart`. Имя
пользователя создаёт cloud-init из seed, и на сборке его нет. Тот же довод,
по которому пользователя cloud-init в группы и автологин вносит
`bisquite-desktop.service` на устройстве, а не сборка.

Сессии в этот момент ещё нет — юнит стоит **до** дисплей-менеджера. Поэтому
`gsettings` запускается через `dbus-run-session`: dconf пишет через свою
службу на шине сеанса, временная шина её заменяет, а записи всё равно уходят
в `~/.config/dconf/user`, откуда их прочтёт будущая сессия. `HOME` задаётся
явно: `runuser` без `-l` окружение не меняет, и с `HOME=/root` настройки
уехали бы в dconf рута — молча и мимо цели.

Порядок «до дисплей-менеджера» несущий: отработай юнит после, vino поднялся
бы только со следующего входа в сессию, то есть после перезагрузки платы.

С другой стороны юнит стоит `After=cloud-final.service`, а **не**
`After=cloud-init.service`, и это тоже замер, а не вкус: `cloud-init.service`
— вторая стадия из четырёх, пользователя на ней ещё нет (его создаёт
`cloud-config`). Замер 2026-09-06 на Jetson Nano: службы с
`After=cloud-init.service` отсчитывали 40 попыток по 3 секунды и сдавались
за две секунды до финиша `cloud-final`. Цикл ожидания при этом остался —
упорядочивание сокращает ожидание, но не заменяет проверку.

### Почему автозапуск `.desktop`, а не `systemctl --user enable`

Юнит у пакета есть — `/usr/lib/systemd/user/vino-server.service`, — но у него
**нет секции `[Install]`**: `systemctl --user enable` отвечает «no
installation config» и ничего не включает. Юнит рассчитан на активацию по
D-Bus (`Type=dbus`, `BusName=org.gnome.Vino`), то есть на запуск по
требованию.

Штатного автозапуска у пакета тоже нет: `.desktop` лежит
в `/usr/share/applications` с `NoDisplay=true`, а не в `/etc/xdg/autostart`.
Поэтому копия в `~/.config/autostart` — единственный способ поднять vino
на безголовой плате, а не костыль.

**Файл именно копируется, а не пишется заново.** Путь к бинарю зависит от
выпуска (замер по пакетам 2026-09-03):

| Выпуск | Версия | `Exec=` в `.desktop` |
|---|---|---|
| focal 20.04 | 3.22.0-5ubuntu2.2 | `/usr/lib/vino/vino-server --sm-disable` |
| noble 24.04 | 3.22.0-6ubuntu5 | `/usr/libexec/vino-server --sm-disable` |

Свой `.desktop` с прибитым путём — ровно тот класс дефекта, который уже был
у `x11vnc` с прибитым путём к X authority: работает до первой смены выпуска
и ломается молча.

## Wayland

**vino обслуживает X11 и на Wayland-сессии бесполезен.** Связь с соседним
расширением здесь несущая и в манифестах не выражается: Xorg включает
десктопное расширение — `gnome` пишет `WaylandEnable=false` в тот файл GDM,
который этот дистрибутив действительно читает (`daemon.conf` у Debian,
`custom.conf` у Ubuntu). Поставите vino поверх сессии на Wayland — сервер
запустится и не покажет ничего.

Проверить на плате:

```console
$ loginctl show-session "$(loginctl list-sessions --no-legend | awk 'NR==1{print $1}')" -p Type
Type=x11
```

## Соседство с x11vnc

Конфликт в манифесте **не объявлен**, и это решение.

Мешают друг другу не расширения, а их умолчания: оба берут порт 5900, и
второй сервер его просто не займёт. Разводится это параметром
(`VINO_PORT=5901` либо `X11VNC_PORT=5901`), то есть препятствие снимается
без правки кода. Вдобавок `conflicts` в bisquite ничего не запрещает — поле
только печатается (`bs extension ls`, `bs extension check`), так что запись
была бы утверждением «эти двое несовместимы», а оно неверно.

Держать оба сервера на одном дисплее разумно редко, но технически возможно.
Ставить оба на один порт — нет.

## Отказы

**`VINO_PORT` вне 5000–50000** и **`VINO_ENCRYPTION` не `true`/`false`** —
отказ на сборке, до установки пакетов.

**Нет пакета `vino` в репозитории образа** — `apt-get install` падает, и
сборка вместе с ним. Замер по архиву Ubuntu 2026-09-03: исходник `vino`
публикуется от precise до questing (25.10), в focal — в `main`, начиная
с jammy — в `universe`. На Debian состав репозиториев другой, проверяйте
до сборки.

**Нет `configure.sh`, юнита или `lib/get_cloud_user.sh` рядом** — отказ: без
первой загрузки vino не запустится ни при каком параметре.

На первой загрузке отказом (кодом возврата 1) заканчиваются: отсутствие
`gsettings`, `dbus-run-session` или `runuser`; отсутствие
`/usr/share/applications/vino-server.desktop` (пакет не установлен);
не дождались пользователя cloud-init за 40 попыток по 3 секунды; нет
домашнего каталога; не применился любой из ключей `gsettings`.

## Ограничения

Фаза `build` требует совпадения архитектур хоста и образа — libguestfs не
выполняет код в госте чужой архитектуры. Для Jetson это значит сборку на
arm64-хосте. Фаза `firstboot` архитектуру не ограничивает: она выполняется
на самом устройстве.

**Каталог `/opt/bisquite/vino-vnc` обязан остаться в образе.**
`configure-vino-vnc.service` зовёт `configure.sh` по этому пути в рантайме,
а не копирует его куда-то «к себе». Инструкция `EXTENSION` кладёт каталог
именно туда; слой, который вычистит `/opt/bisquite`, сломает настройку —
причём не на сборке, а на первой загрузке.

Расширение **не** поднимает дисплей-менеджер, не настраивает автологин и не
выключает Wayland — это работа десктопного расширения. vino живёт внутри сессии
пользователя, поэтому без `DESKTOP_AUTOLOGIN=1` (ручка десктопного расширения
или `cloud-user-desktop`, с 2.0.0 по умолчанию выключена) до входа человека
VNC не поднимется. Оно также не
открывает порт в межсетевом экране.

## Проверка

На собранном образе:

```console
$ virt-cat -a образ.qcow2 /etc/bisquite/vino/config
$ virt-ls -a образ.qcow2 /etc/systemd/system | grep vino
```

На плате после первой загрузки:

```console
$ systemctl status configure-vino-vnc.service
$ gsettings list-recursively org.gnome.Vino
$ ss -ltnp | grep 5900
$ pgrep -a vino-server
```

Ожидаемое при умолчаниях — `127.0.0.1:5900`; при `VINO_LISTEN=all` —
`0.0.0.0:5900`.
