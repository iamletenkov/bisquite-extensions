# sensing-gmsl2-camera

Драйверы камер Sensing GMSL2 для **Jetson AGX Orin Developer Kit** (модуль
p3701-0000, носитель p3737-0000) с адаптером **SG8A-AGON-G2Y-A1**: замена
ядра, модули `.ko`, DTB-оверлей, новая запись в загрузочном меню.

## Манифест

| Поле | Значение |
|---|---|
| `phase` | `build` (запуск камер — своими юнитами на каждой загрузке, не firstboot) |
| `arch` | `arm64` |
| `provides` | `gmsl2-camera` |
| `requires` | пусто |
| `conflicts` | пусто |

## Зачем это слой, а не часть базового образа

Камеры — свойство конкретного адаптера на конкретных роботах, а не платы
Jetson вообще. Образ из BSP (`jetson-orin-bsp`) остаётся общим для всего
флота; этот слой ложится только на VMFILE тех машин, где адаптер физически
установлен.

## Что делает

1. Проверяет, что это именно AGX Orin с адаптером `p3737-0000+p3701-0000` —
   по наличию `/boot/dtb/kernel_tegra234-p3737-0000+p3701-0000-nv.dtb` в
   уже собранном базовом образе. `/proc/device-tree` для этого не годится:
   внутри `virt-customize` гость не загружен, это chroot поверх файловой
   системы, а не работающая Tegra.
2. Клонирует `SENSING-Technology/nvidia-jetson-camera-drivers` и берёт
   пакет `..._GMSL2x8_...` (не `_YUV_` — с ним камера `SG2-AR0233C-5200-G2A`
   не работает, `sensor_probe detect error` на всех восьми портах; разбор —
   в `nvidia-jetpack/scripts/02-fetch-camera-drivers.sh`).
3. Бэкапит штатное ядро в `/boot/Image.backup` (идемпотентно — `cp -n`),
   заменяет `/boot/Image` на ядро Sensing.
4. Кладёт `.ko`-модули в `/lib/modules/5.15.148-tegra/updates/...`, снимает
   штатный `max96712.ko`.
5. Копирует DTB-оверлей в `/boot/`.
6. Кладёт весь пакет драйверов в `/opt/sensing` — для диагностики
   и ручного `quick_bring_up.sh`, если понадобится другой профиль.
7. Правит `/boot/extlinux/extlinux.conf`: добавляет запись `JetsonIO`
   с оверлеем и делает её умолчанием, добавляет резервную запись `backup`
   на `/boot/Image.backup` — с **тем же** `root=`, что и у исходной записи
   (вендор в своём примере даёт `backup` без `root=` вовсе — такая запись
   не загрузится). Существующий `root=PARTUUID=...` не трогает: он
   переносится дословно в обе новые записи.
8. Кладёт неинтерактивную замену `quick_bring_up.sh`, которая срабатывает
   сама на каждой загрузке (разбор ниже).

## Запуск камер: без него кадров нет

Модули ядро грузит само, по дереву устройств, — **без параметров**. Замер
на плате 2026-09-14, образ без шага 8: `/dev/video0..7` на месте,
`max96712_probe: probe success` на обоих дешериализаторах, и при этом на
всех восьми портах `sensor_probe … detect error`, `link:0x02`, а кадры —
одна и та же заглушка по 24 КБ. Модуль получил `GMSLMODE=0,0,0,0`, то есть
GMSL1, а камеры — GMSL2. Узлы есть, картинки нет, и снаружи это выглядит
исправным.

Вендор доводит это интерактивно в `quick_bring_up.sh`. Расширение делает
то же самое без вопросов:

| Что | Чем | Когда применяется |
|---|---|---|
| режим линка (`GMSLMODE`) | `/etc/modprobe.d/bisquite-sensing-gmsl2.conf` | при загрузке модуля — после правки перезагрузка |
| профиль камеры (`v4l2-ctl -c sensor_mode=…`) | правило udev → `bisquite-sensing-camera@videoN.service` | на появление каждого узла, в том числе после `rmmod`/`modprobe` |
| частоты VI/ISP/NVCSI/EMC на максимум (`boost_clock.sh`) | `bisquite-sensing-clock.service` | на каждой загрузке |

**Номер порта знать не нужно** — прежний довод «порт известен только на
месте» к запуску не относится. Профиль ставится на все узлы драйвера:
на пустом порту `v4l2-ctl` проходит без вреда (rc=0), а узлы чужих
драйверов (USB-камеры) скрипт опознаёт по `Card type` и пропускает.
Модель камеры — параметр: на роботах одного профиля она одна.

С шагом 8, та же плата после перезагрузки: порт камеры даёт `link:0xc8`
без `detect error`, 10 разных кадров по ~217 КБ, аппаратная запись H.265
1080p с камеры через `nvv4l2h265enc`.

**Поменять на работающей машине:**

```bash
sudoedit /etc/default/bisquite-sensing-camera        # профиль, частоты
sudo systemctl restart 'bisquite-sensing-camera@*' bisquite-sensing-clock
sudoedit /etc/modprobe.d/bisquite-sensing-gmsl2.conf # режим линка
sudo reboot
```

**Найти, на каком порту камера** (для диагностики, работе не нужно):
рабочий порт — тот, где **нет** строки `sensor_probe ... detect error`,
а `dser_link_check link:` даёт `0xc8`, а не `0x02`. У нас камера из
кабеля CN2 оказалась на `/dev/video6`, а не на ожидаемом `/dev/video5`.
Проверка без X: `gst-launch-1.0 v4l2src device=/dev/videoN num-buffers=10
! jpegenc ! multifilesink location=/tmp/f_%02d.jpg` — живая камера даёт
разные хеши, пустой порт одинаковые файлы.

## Переменные окружения

| Переменная | Умолчание | Что делает |
|---|---|---|
| `SENSING_CAMERA_PKG_REL` | `Jetson AGX Orin Devkit/SG8A-AGON-G2Y-A1/JetPack6.2/SG8A_AGON_G2Y_A1_AGX_Orin_GMSL2x8_JP6.2_L4TR36.4.3` | путь к пакету драйверов внутри клона Sensing |
| `SENSING_GMSLMODE` | `1,1,1,1,1,1,1,1` | режим линка по портам 0–7: `0`=GMSL1, `1`=GMSL2 6 Гбит/с, `2`=GMSL2 3 Гбит/с |
| `SENSING_CAMERA_CONTROLS` | `sensor_mode=1,trig_mode=0,trig_pin=0x00020007` | профиль камеры; умолчание — пункт 3 меню вендора, `SG2-AR0233-5200-G-Hxxx`. Другая модель — строка из `quick_bring_up.sh` для её номера |
| `SENSING_BOOST_CLOCK` | `1` | `0` — не фиксировать частоты SoC на максимуме (меньше потребление, вендор так не делает) |

Неверный формат любого из трёх — отказ на сборке, а не молча
неработающие камеры.

## Проверено

Ручной прогон той же последовательности — живая плата, JetPack 6.2,
L4T 36.4.3, 2026-09-11: живое видео 1920×1080 UYVY с `/dev/video6`,
`root=PARTUUID` пережил и заливку, и наложение тестового слоя через
`virt-customize`.

Само расширение (файловые операции + `virt-customize`, без реальной платы)
на момент написания не прогонялось до конца пайплайна `bs image build` —
см. `docs/plans/2026-09-11-jetson-image-pipeline.md` в основном
репозитории.
