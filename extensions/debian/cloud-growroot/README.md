# cloud-growroot

Включает модули cloud-init `growpart` и `resizefs`, без которых корень не
растёт до размера носителя. Правит список `cloud_init_modules` в самом
`/etc/cloud/cloud.cfg` в фазе сборки; ни службы, ни шага первой загрузки
у расширения нет.

## Манифест

| Поле | Значение |
|---|---|
| `phase` | `build` (только; на первой загрузке уже поздно — см. «Ограничения») |
| `arch` | `amd64`, `arm64` |
| `provides` | `cloud-growroot` |
| `requires` | пусто — нужные утилиты расширение проверяет само, а не объявляет способностью |
| `conflicts` | пусто |

## Зачем

**Отказ тихий.** cloud-init отрабатывает успешно и рапортует `SUCCESS`,
потому что со своей точки зрения делает всё, что ему поручено: модулей,
читающих `growpart:` и `resize_rootfs:` из seed, просто нет в списке
запускаемых.

Замер 2026-09-03, Raspberry Pi OS Trixie на карте 58 ГБ. Корень остался
11.5 ГБ при 46 ГБ свободного места:

```
sdb2  start 1064960    size 24100864   ← корень, 11.5 ГБ
                       ...46 ГБ свободно...
sdb3  start 121331712  size 204800     ← cidata, у самого конца
```

**Причина не в пакетах.** В образе стоят `cloud-init`, `cloud-guest-utils`
и `e2fsprogs`, бинарники `/usr/bin/growpart` и `/sbin/resize2fs` на месте.
Дело в том, что список `cloud_init_modules` в `/etc/cloud/cloud.cfg` у Pi OS
не содержит ни `growpart`, ни `resizefs`, — значит `growpart:` и
`resize_rootfs:` из seed читать некому.

Своего механизма у образа тоже нет: `raspberrypi-sys-mods/firstboot`
и `resize2fs_once` в нём отсутствуют — конкурента у cloud-init не будет.

## Кому нужно

| Образ | Нужно |
|---|---|
| Raspberry Pi OS | **да** — модулей в списке нет |
| Ubuntu Server / cloud | нет — модули в каноническом `cloud.cfg` уже есть |

На образе, где оба модуля уже включены, расширение говорит об этом и
**ничего не меняет** (выходит с нулём) — подключать его «на всякий случай»
безвредно, но и бессмысленно.

## Подключение

```vmfile
EXTENSION cloud-growroot
```

Переменных окружения расширение не читает, аргументов не принимает:
настраивать тут нечего — либо модули в списке есть, либо их туда вписывают.
Порядок относительно других расширений безразличен с одной оговоркой: если
`growpart` и `resize2fs` приходят слоем `INSTALL`, он обязан стоять **до**
этой строки, иначе расширение откажет (см. «Отказы»).

## Что делает

Вписывает `growpart` и `resizefs` в `cloud_init_modules` **самого
`/etc/cloud/cloud.cfg`**, сразу после элемента `write_files` (принимается и
написание `write-files` — имя модуля менялось между версиями cloud-init).
Там же они стоят в каноническом файле Ubuntu, и это до `disk_setup`/`mounts`:
расширять раздел надо раньше, чем на него что-то смонтируют.

```yaml
cloud_init_modules:
  - write_files
  - growpart       # ← вписывается здесь
  - resizefs       # ←
  - disk_setup
  - mounts
```

Прежний файл сохраняется как `/etc/cloud/cloud.cfg.before-growroot` —
и сохраняется он **только когда файл действительно меняется**. Копия
снимается после проверки якоря и до единственной необратимой строки (`mv`),
потому что порядок «проверить → портить» здесь и есть весь запас отката.
Пока копия снималась раньше проверки, прогон с ненайденным якорем оставлял
`cloud.cfg.before-growroot` при нетронутом `cloud.cfg`: след от правки,
которой не было, а читается он ровно наоборот.

**Почему не файлом в `cloud.cfg.d`.** `util.read_conf_d` сливает фрагменты
через `mergemanydict`, а тот списки **не склеивает**: побеждает целиком тот,
что старше по приоритету. Фрагмент с `cloud_init_modules: [growpart, resizefs]`
заменил бы весь список и унёс бы `users_groups`, `ssh` и `set_passwords` —
карта пришла бы без пользователя и без ключей. Лечение оказалось бы хуже
болезни.

**Отступ берётся у строки-якоря, а не пишется константой.** С жёстко
вписанным одним пробелом получается смесь одно- и двухпробельных элементов
одного блока, а это невалидный YAML: `cloud.cfg` перестаёт разбираться
целиком — и лечение опять выходит хуже болезни.

## Отказы

**Нет `/etc/cloud/cloud.cfg`** — cloud-init не установлен; без него ни корень
не вырастет, ни seed не прочитается.

**Нет `growpart` или `resize2fs`** — отказ, а не предупреждение: включённый
модуль без своей утилиты промолчит уже на устройстве, а это ровно тот исход,
который расширение и чинит. Сообщение называет пакеты (`cloud-guest-utils`,
`e2fsprogs`) и говорит поставить их слоем `INSTALL` выше.

**Не нашёлся якорь `write_files` внутри `cloud_init_modules`** — список
устроен иначе, чем ожидалось. Расширение не угадывает место вставки: порядок
модулей несущий. После такого отказа в `/etc/cloud/` не остаётся **ничего**:
ни изменённого `cloud.cfg`, ни `cloud.cfg.new`, ни `cloud.cfg.before-growroot`.

## Ограничения

`phase: [build]`, то есть архитектуры хоста и образа обязаны совпасть. Сама
правка конфигурации архитектуры не касается — ограничение вносит форма
расширения: фаза `build` означает «выполняется код в госте», а libguestfs
требует совпадения хоста и гостя.

**Фазы первой загрузки у расширения нет, и это тоже намеренно.** На ней уже
поздно: cloud-init читает `cloud_init_modules` раньше, чем что-либо успело
бы его поправить. Следствие для оператора — **переконфигурировать нечего**:
ни службы, ни файла времени выполнения расширение не заводит, перезапускать
после правки ничего не нужно. Если правку надо внести на живой машине, это
тот же `/etc/cloud/cloud.cfg` и перезагрузка.

**Корень вырастет до начала раздела `cidata`, а не до конца носителя.**
Писалка создаёт seed-раздел в конце диска, и между ним и корнем остаётся
всё свободное место — на практике это почти вся карта, но «вырос не до
самого конца» надо понимать заранее, иначе выглядит недоработкой. Расширение
говорит об этом предупреждением в конце работы.

## Проверка

На собранном образе:

```console
$ virt-cat -a образ.qcow2 /etc/cloud/cloud.cfg | grep -A6 cloud_init_modules
```

На устройстве после первой загрузки:

```console
$ lsblk /dev/mmcblk0
$ df -h /
$ grep -i growpart /var/log/cloud-init.log
```
