# jetson-stats

Ставит `jtop` — монитор NVIDIA Jetson: загрузка CPU и GPU, память, частоты,
питание, температуры, вентилятор, режим `nvpmodel`.

## Зачем

На Jetson нет ни `nvidia-smi`, ни `nvtop`, которые работали бы: и то и другое
опирается на NVML, а NVML на Tegra до JetPack 7 не существует (разбор ниже).
Единственный монитор, читающий Tegra её собственными средствами —
`tegrastats` и sysfs, — это `jtop` из пакета `jetson-stats`.

Замер на живой плате, 2026-09-03:

```
Ubuntu 20.04.6 LTS aarch64, ядро 4.9.253-tegra
L4T R32.6.1 (JetPack 4.6.1), плата t210ref, tegra210
jtop:       /usr/local/bin/jtop   (ставится pip-пакетом jetson-stats)
tegrastats: /usr/bin/tegrastats   (из L4T)
nvtop:      нет, и в apt-репозиториях этой машины его нет вовсе
```

## Манифест

| Поле | Значение |
|---|---|
| `arch` | `arm64` |
| `phase` | `build` (`install.sh`), `firstboot` (`configure.sh`) |
| `provides` | `jetson-monitor` |
| `requires` | — |
| `conflicts` | — |

`arch: [arm64]` — не осторожность, а форма железа: Jetson существует только
как aarch64-модуль на Tegra. С PyPI приезжает колесо `py3-none-any`, то есть
на amd64 пакет **поставился бы** и был бы мёртвым грузом — поэтому ось ловит
несовпадение до сборки, а случай «arm64, но не Jetson» ловит уже `install.sh`
по `/etc/nv_tegra_release`.

## Подключение

```vmfile
EXTENSION jetson-stats
```

Прежняя запись продолжает работать:

```vmfile
COPY_IN <чекаут>/extensions/debian/jetson-stats:/opt/vmsetup/
RUN_COMMAND chmod +x /opt/vmsetup/jetson-stats/*.sh
RUN_COMMAND /opt/vmsetup/jetson-stats/install.sh
```

`<чекаут>` — путь до чекаута этого репозитория **относительно каталога
VMFILE**; в примерах основного репозитория это `../../../../bisquite-extensions`,
и глубина зависит от того, насколько глубоко лежит сам VMFILE.

## Параметры

| Переменная | Умолчание | Что делает |
|---|---|---|
| `JETSON_STATS_VERSION` | пусто — последняя с PyPI | версия пакета: `pip3 install -U jetson-stats==X.Y.Z` |

Других переменных ни `install.sh`, ни `configure.sh` не читают.

```vmfile
EXTENSION jetson-stats JETSON_STATS_VERSION=7.2.1
```

Пин не «на всякий случай»: ветки 4.x и 7.x ставят службу по-разному (см.
следующий раздел), и закрепиться на проверенной версии — единственный способ
повторить сборку через полгода.

## Что делает

- **Сборка** (`install.sh`) — отказывает, если образ не L4T; ставит
  `python3-pip` и `python3-setuptools` (документированное требование
  upstream), затем `pip3 install -U jetson-stats` (пять попыток
  с нарастающей паузой); добивается, чтобы появился
  `/etc/systemd/system/jtop.service`, и включает его; заводит группу `jtop`,
  если её нет; ставит и включает `configure-jetson-stats.service`.
- **Первая загрузка** (`configure.sh`) — вносит пользователя cloud-init
  в группу `jtop` и проверяет, что демон работает. Юнит — `oneshot`
  с `RemainAfterExit=yes`, но отрабатывает на **каждой** загрузке; повторный
  прогон идемпотентен («уже в группе jtop»).

Группу `jtop` заводит именно сборка, и это не дубль: `jtop --install-service`
создаёт её сам, а при копировании юнита руками (заходы 3 и 4) её не создаёт
никто, и служба падает на старте с «Group jtop does not exist!»
(`jtop/service.py:627`). `configure.sh` на всякий случай заводит её тоже, но
говорит об этом предупреждением — это работа `install.sh`.

`yq` этому расширению **не нужен**, в отличие от десктопов: `configure.sh`
проверяет только наличие исполняемого `get_cloud_user.sh` рядом, а тот без
`cloud-init`/`yq` уходит на запасной путь — первая учётка с uid 1000..65533
и домашним каталогом.

### Почему pip, а не apt

Пакета `jetson-stats` в репозиториях Ubuntu нет: проект живёт на PyPI, и
его README документирует ровно один способ — `sudo pip3 install -U
jetson-stats`, а перед ним `apt install python3-pip python3-setuptools`.
Расширение повторяет обе строки.

На Ubuntu 24.04 и новее pip отказывается ставить в системный интерпретатор
без `--break-system-packages` (PEP 668); upstream документирует это
отдельным пунктом. Расширение смотрит на сам маркер
(`/usr/lib/python3*/EXTERNALLY-MANAGED`), а не на версию дистрибутива —
маркер и есть то, на что смотрит pip.

### Почему службу приходится ставить руками

`jtop` — клиент; данные ему отдаёт демон через сокет `/run/jtop.sock`.
Без `jtop.service` команда отвечает «The jtop.service is not active»
(`jtop/jtop.py:1116`).

Раньше службу ставил сам pip: `setup.py` объявляет команду `build_py`,
которая копирует `services/jtop.service` в `/etc/systemd/system`, зовёт
`systemctl enable` и заводит группу `jtop`.

**Замер по артефактам PyPI (2026-09-03):**

| Версия | Что опубликовано | Ставит ли pip службу |
|---|---|---|
| … 4.3.2 (19.03.2025) | только sdist | да — pip собирает колесо сам, `build_py` выполняется |
| 7.2.0 (14.07.2026) | sdist **и** `py3-none-any.whl` | **нет** — pip берёт готовое колесо |
| 7.2.1 (09.08.2026) | sdist **и** `py3-none-any.whl` | **нет** |

Из готового колеса `build_py` не выполняется никогда. Поэтому
`pip3 install -U jetson-stats` сегодня оставляет систему с установленным
клиентом и без демона.

Расширение проверяет **факт** (есть ли файл юнита), а не версию, и добивается
его четырьмя заходами подряд:

1. после `pip3 install` — вдруг уже есть (ветка sdist);
2. `jtop --install-service` — штатная команда проекта
   (`jtop/__main__.py:174`): ставит `/etc/profile.d/jtop_env.sh`, заводит
   группу `jtop` и копирует юнит, находя шаблон в data-файлах колеса
   (`/usr/local/share/jetson_stats/jtop.service`);
3. копирование того же шаблона руками —
   `/usr/local/share/jetson_stats/jtop.service` или
   `/usr/share/jetson_stats/jtop.service`;
4. юнит пишется самим расширением по эталону с живой платы — разбор
   в разделе «Откуда берётся `jtop.service`».

Не помог ни один — **отказ сборки**. «Поставилось, но не работает»
обнаружилось бы на плате, после записи карты.

### Почему нужна фаза firstboot

Демон выставляет сокету права `0660 root:jtop` (`jtop/service.py`,
`JtopServer.start`). Пользователь вне группы `jtop` получает от клиента
не подсказку, а сбивающее с толку «I can't access jtop.service. Please
logout or reboot this board» (`jtop/jtop.py:1117`) — и перезагрузка не
помогает, потому что дело не в ней.

Кого вносить в группу, на сборке неизвестно: пользователя создаёт cloud-init
из seed уже на устройстве. Тот же довод, по которому автологин настраивается
на первой загрузке.

Членство в группе применяется при входе в сессию. Если автологин уже
случился, в текущей сессии `jtop` ещё откажет — расширение говорит об этом
предупреждением в журнале.

## Почему НЕ nvtop

Коротко: `nvtop` не умеет Tegra ни в одной версии, а не «умеет начиная
с 3.x». Проверено по исходникам и по архиву Ubuntu 2026-09-03.

**1. Бэкенда Tegra в nvtop нет вовсе.** В дереве тега 3.3.2 (последний релиз,
опубликован 08.02.2026) слов `tegra`, `jetson` и `nvgpu` нет ни одного —
ни в коде, ни в README, ни в CMake. Бэкенды перечислены каталогом `src/`:
amdgpu, radeon, intel (i915 и xe), msm, panfrost, panthor, v3d, apple,
ascend, ixml, metax, enflame, tenstorrent, tpu, rockchip. Tegra среди них
нет.

**2. NVIDIA у nvtop — это NVML и только он.** Бэкенд грузит библиотеку
драйвера: `dlopen("libnvidia-ml.so")`, при неудаче `"libnvidia-ml.so.1"`
(`src/extract_gpuinfo_nvidia.c:275,277`). README проекта в разделе
зависимостей говорит то же: «For NVIDIA: the *NVIDIA Management Library*
(*NVML*) which comes with the GPU driver», а в разделе про неполадки —
что без этой библиотеки будет `NO GPU to monitor`.

**3. NVML на Tegra до JetPack 7 нет.** Это видно из кода самого
jetson-stats: к NVML он тянется **только** на JetPack 7 / L4T R38 и новее
(`jtop/core/gpu.py`, ветка `is_jetpack7()`; порог объявлен в
`jtop/core/hw_detect.py`: `JETPACK7_L4T_MAJOR = 38`). На всём, что старше —
а Nano это R32, JetPack 4.6.1, и новее для него не выйдет, — данные берутся
из `tegrastats` и sysfs. То есть upstream-монитор Jetson сам считает NVML
доступным только с JetPack 7.

Проверяется на плате одной командой:

```console
$ ldconfig -p | grep libnvidia-ml   # на Nano пусто
```

**4. В focal лежит nvtop 1.0.0, и он в multiverse.** Замер по Launchpad
(`getPublishedSources`, 2026-09-03):

| Выпуск Ubuntu | Версия nvtop | Компонент |
|---|---|---|
| focal (20.04) | 1.0.0-1ubuntu2 | multiverse |
| jammy (22.04) | 1.2.2-1 | multiverse |
| noble (24.04) | 3.0.2-1 | multiverse |

То есть даже с включённым `multiverse` на 20.04 приезжает сборка 2020 года —
и она тоже NVML-only. На замеренной плате `multiverse` не включён, поэтому
`apt` не находит `nvtop` вовсе.

**Что из исходного утверждения не подтвердилось:** «поддержка Tegra
появилась только в nvtop 3.x». Её нет и в 3.3.2. Остальное подтвердилось:
1.x в focal — да (с уточнением про multiverse), опора на NVML — да,
3.3.2 — последний релиз — да.

## Откуда берётся `jtop.service`

Пакет его **не поставляет**. С 7.2.0 на PyPI лежит готовое колесо
`py3-none-any`, а хук `build_py`, который раньше ставил юнит, из колеса
не выполняется; data-файлов `services/` и `share/jetson_stats/` в колесе
тоже нет.

Расширение добивается юнита четырьмя заходами подряд, останавливаясь
на первом сработавшем:

| | способ | когда срабатывает |
|---|---|---|
| 1 | хук pip | установка из sdist, до 4.3.2 включительно |
| 2 | `jtop --install-service` | если команда есть и отрабатывает |
| 3 | копия шаблона из data-файлов пакета | если они поставлены |
| 4 | **пишем сами** | нынешние версии — единственный рабочий |

Содержимое четвёртого не выдумано: снято с **живого Jetson Nano**
(2026-09-03), где jtop 7.2.1 работает, а юнит в `/etc/systemd/system`
написан руками — ровно потому, что пакет его не несёт. Путь к `jtop`
резолвится через `command -v`, а не прибивается: `sudo pip3` кладёт его
в `/usr/local/bin`, а pip в venv — в другое место.

## Отказы

**Нет `/etc/nv_tegra_release`** — образ не L4T. Отказ, а не предупреждение:
`jtop` там не заработает никогда, а поставленный молча он выглядит рабочей
командой, которая всегда падает. Это тот же файл, по которому опознаёт плату
сам jetson-stats (`jtop/core/jetson_variables.py:240`).

**Не удалось поставить пакет с PyPI** — пять попыток с нарастающей паузой,
потом отказ.

**Не появился `jtop.service`** — после всех четырёх заходов. Отказ сборки.
Отдельный случай того же: четвёртый заход невозможен, если `jtop` не нашёлся
в `PATH` после установки — писать юнит не на что.

**Нет `configure-jetson-stats.service` рядом со скриптом** — без него
пользователь не попадёт в группу `jtop`, и команда на плате будет отвечать
отказом доступа.

На первой загрузке отказом (кодом возврата 1) заканчиваются три случая:
рядом нет исполняемого `get_cloud_user.sh`; не дождались пользователя
cloud-init за 40 попыток по 3 секунды; `jtop.service` не запустился.
Последний — без `|| true` намеренно: неработающий демон означает, что команда
`jtop` на плате не работает вовсе, а расширение при этом отрапортовало бы
успехом.

## Ограничения

**`arch: [arm64]`** и `phase: build` вместе означают, что **собирать надо на
arm64-хосте**: libguestfs не выполняет код в госте чужой архитектуры, а
установка идёт кодом внутри гостя. На amd64-машине сборка отвергается до
начала, с объяснением.

**Сеть нужна на машине сборки**, а не на плате: пакет приезжает с PyPI
в момент сборки и запекается в образ. Это и есть смысл фазы `build` —
все устройства тиража получают одну и ту же версию.

Расширение **не** ставит CUDA, драйверы и ничего не переключает в
`nvpmodel`. Оно даёт монитор, а не режим питания.

## Где стоит юнит донастройки, и почему именно там

`configure-jetson-stats.service` объявлен `After=cloud-final.service` /
`Wants=cloud-final.service` и привязан `WantedBy=cloud-init.target`. Обе
строки — результат замеров, а не вкус, и менять их нельзя, не повторив замеры:

- **`After=cloud-init.service` не годится.** `cloud-init.service` — вторая
  стадия из четырёх, пользователя на ней ещё нет: его создаёт `cloud-config`,
  а заканчивает всё `cloud-final`. Замер 2026-09-06 на Jetson Nano: службы
  с `After=cloud-init.service` отсчитывали 40 попыток по 3 с и сдавались
  **за две секунды** до финиша `cloud-final`.
- **`WantedBy=multi-user.target` не годится** вместе с
  `After=cloud-final.service`: сам `cloud-final` объявлен
  `After=multi-user.target`, кольцо systemd разрывает, **молча** выбрасывая
  нашу задачу (замер 2026-09-06: так выбросило сразу три службы).
  `cloud-init.target` объявлен `After=cloud-final.service` — он для этого
  и существует.
- **`After=jtop.service` убран** по той же причине: вендорский `jtop.service`
  стоит `After=multi-user.target`, и кольцо
  `multi-user.target → configure-jetson-stats → jtop.service → multi-user.target`
  systemd разрывал тем же способом — одна строка в журнале, служба не
  выполнялась ни разу (замер 2026-09-04 на живом Nano). Ждать `jtop.service`
  и не нужно: `configure.sh` работает с установленным пакетом и группой,
  а не с запущенной службой.

Вывод для того, кто правит юнит: **молчаливое выбрасывание задачи** — штатная
реакция systemd на цикл, поэтому любое новое `After=` проверяется не чтением,
а `journalctl -b | grep -i 'ordering cycle'` на живой плате.

## Что править и чем перезапускать

| Что менять | Где лежит на устройстве | Чем применить |
|---|---|---|
| параметры демона jtop | `/etc/systemd/system/jtop.service` | `systemctl daemon-reload && systemctl restart jtop.service` |
| кто имеет доступ к `/run/jtop.sock` | членство в группе `jtop` (`usermod -aG jtop <user>`) | новый вход в сессию (`logout`/`reboot`) — сессия группу на ходу не подхватывает |
| что делает донастройка | `/opt/vmsetup/jetson-stats/configure.sh` | `systemctl restart configure-jetson-stats.service` |
| переменные окружения jtop | `/etc/profile.d/jtop_env.sh` (кладёт `jtop --install-service`, захода 2) | новый вход в сессию |

Версия пакета — параметр **сборки**, а не устройства: на плате её меняют
только `pip3 install -U jetson-stats==X.Y.Z` вручную, и такая правка уедет
при следующей перезаписи носителя.

## Проверка

На собранном образе:

```console
$ virt-ls -a образ.qcow2 /etc/systemd/system | grep jtop
$ virt-cat -a образ.qcow2 /etc/systemd/system/jtop.service
$ virt-ls -a образ.qcow2 /usr/local/bin | grep jtop
```

На плате после первой загрузки:

```console
$ systemctl is-active jtop.service
$ id -nG | tr ' ' '\n' | grep -x jtop     # пользователь в группе
$ jtop                                     # без sudo
$ jetson_release                           # сводка по плате
```
