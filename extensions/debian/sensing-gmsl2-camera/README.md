# sensing-gmsl2-camera

Драйверы камер Sensing GMSL2 для **Jetson AGX Orin Developer Kit** (модуль
p3701-0000, носитель p3737-0000) с адаптером **SG8A-AGON-G2Y-A1** на
**L4T 36.4.3** (JetPack 6.2): библиотека ISP из оверлея камер NVIDIA, замена
ядра, модули `.ko`, DTB-оверлей, новая запись в загрузочном меню.

> **С 4.0.0 — всё про камеры только здесь.** Базовый образ из
> `nvidia-jetpack` камер больше не несёт (решение владельца 2026-09-18):
> ни `/opt/sensing`, ни подменённой `libnvisppg.so`, ни пакетов камер.
> Расширение само скачивает оверлей камер NVIDIA `overlay_camera_36.4.3.tbz2`,
> сверяет его с закреплённой sha256 и подменяет `libnvisppg.so` через
> `dpkg-divert`. Два следствия для VMFILE: сборке нужна сеть до
> `developer.nvidia.com`, и расширение **отказывает на любом L4T, кроме
> 36.4.3** — раньше оно проверяло только плату.

> **С 2.1.0 — раскладка 2.** Манифест объявляет `layout: 2`: каталог расширения
> в госте — `/opt/bisquite/sensing-gmsl2-camera/` (был `/opt/vmsetup/sensing-gmsl2-camera/`). Путей гостя
> расширение не прибивает, поэтому версия минорная; нужен bisquite
> с поддержкой `layout: 2`.

> **С 3.0.0 — библиотека настроек.** `/etc/bisquite/sensing-camera/config` —
> домен `sensing-camera` библиотеки `bisquite-conf` (схема `knobs`):
> `bisquite-sensing-camera-ctl` больше **не исполняет** файл (`. "$CONF"` —
> строка `$(…)` в нём выполнялась от root на каждое появление узла), значения
> проверяются, установка файл не переписывает. CLI ставится ссылкой в каталог
> расширения.

**С 2.0.0 файл ручек — `/etc/bisquite/sensing-camera/config`** (был
`/etc/default/bisquite-sensing-camera`). Прежний путь не читается; если
файл по нему остался в базовом образе, установка его удаляет.

## Манифест

| Поле | Значение |
|---|---|
| `phase` | `build` (запуск камер — своими юнитами на каждой загрузке, не firstboot) |
| `arch` | `arm64` |
| `provides` | `gmsl2-camera` |
| `requires` | пусто |
| `conflicts` | пусто |

## Зачем это слой, а не часть базового образа

Камеры — свойство конкретного адаптера на конкретных роботах, а не платы
Jetson вообще. Образ из BSP (`jetson-orin-bsp`) остаётся общим для всего
флота; этот слой ложится только на VMFILE тех машин, где адаптер физически
установлен.

## Что делает

1. Проверяет, что это именно AGX Orin с адаптером `p3737-0000+p3701-0000` —
   по наличию `/boot/dtb/kernel_tegra234-p3737-0000+p3701-0000-nv.dtb` в
   уже собранном базовом образе. `/proc/device-tree` для этого не годится:
   внутри `virt-customize` гость не загружен, это chroot поверх файловой
   системы, а не работающая Tegra. Там же, до сети, — релиз: первая строка
   `/etc/nv_tegra_release` обязана дать ровно `36.4.3`.
2. Скачивает оверлей камер NVIDIA и подменяет `libnvisppg.so` — раздел
   «Библиотека ISP» ниже.
3. Клонирует `SENSING-Technology/nvidia-jetson-camera-drivers` и берёт
   пакет `..._GMSL2x8_...` (не `_YUV_` — разбор ниже, «Почему пакет GMSL2x8»).
4. Бэкапит штатное ядро в `/boot/Image.backup` (идемпотентно — `cp -n`),
   заменяет `/boot/Image` на ядро Sensing; кладёт `.ko`-модули в
   `/lib/modules/5.15.148-tegra/updates/...`, снимает штатный `max96712.ko`.
5. Копирует DTB-оверлей в `/boot/`.
6. Кладёт весь пакет драйверов в `/opt/sensing` — для диагностики
   и ручного `quick_bring_up.sh`, если понадобится другой профиль.
7. Правит `/boot/extlinux/extlinux.conf`: добавляет запись `JetsonIO`
   с оверлеем и делает её умолчанием, добавляет резервную запись `backup`
   на `/boot/Image.backup` — с **тем же** `root=`, что и у исходной записи
   (вендор в своём примере даёт `backup` без `root=` вовсе — такая запись
   не загрузится). Существующий `root=PARTUUID=...` не трогает: он
   переносится дословно в обе новые записи.
8. Кладёт неинтерактивную замену `quick_bring_up.sh`, которая срабатывает
   сама на каждой загрузке (разбор ниже).

## Библиотека ISP

Штатная `libnvisppg.so` из пакета `nvidia-l4t-camera` с этими камерами не
годится; NVIDIA выпускает замену отдельным архивом на каждый релиз —
«оверлеем камер». До 2026-09-19 её подкладывала станция прошивки (шаг `03`
`nvidia-jetpack`), теперь — это расширение:

| Что | Значение (замер 2026-09-19) |
|---|---|
| архив | `https://developer.nvidia.com/downloads/embedded/L4T/r36_Release_v4.3/overlay_camera_36.4.3.tbz2`, 280 128 байт |
| sha256 архива | `acacdf47862b1212fb5ddff2046d49397f9f86757951b15ccde4af5e74f49f3f` |
| sha256 библиотеки из него | `3970c9cc85f86b978fdca1d20f2798c022f6852d26cfe03ae5bceec6ae0666ca` (md5 `5cccbf56…`) |
| sha256 штатной, `nvidia-l4t-camera` 36.4.3 | `7e7c7500fae24da5bbb09dbed8d4235346c5110ab19b78e5daccbd8d078d5a2c` (md5 `bc9fe35d…`) |

Не скачалось или сумма не та — **отказ сборки**, а не пропуск: без этой
библиотеки ISP узлы есть, а картинки нет. В образе на месте штатной
библиотеки должна лежать либо она сама, либо уже подменённая (база, собранная
до 2026-09-19); третье — отказ.

Подмена — через `dpkg-divert --rename`, а не копией поверх: файл принадлежит
`nvidia-l4t-camera`, и слой, который его переустановит или обновит, молча
вернул бы штатную. Отведение кладёт будущую версию из пакета в
`libnvisppg.so.distrib`, туда же уезжает и штатная — это копия для отката.
Путь — `/usr/lib/aarch64-linux-gnu/nvidia/libnvisppg.so`: `tegra/` в L4T 36.x
ссылка на `nvidia/`, а dpkg знает файл только по второму пути.

Проверить на плате и откатить:

```bash
dpkg-divert --list | grep libnvisppg
sha256sum /usr/lib/aarch64-linux-gnu/nvidia/libnvisppg.so    # 3970c9cc…
# откат на штатную:
sudo rm /usr/lib/aarch64-linux-gnu/nvidia/libnvisppg.so
sudo dpkg-divert --rename --remove /usr/lib/aarch64-linux-gnu/nvidia/libnvisppg.so
```

## Почему пакет GMSL2x8, а не YUV

Под JetPack 6.2 у Sensing на эту плату лежат четыре пакета, и различаются
они серединой имени: `_YUV_`, `_GMSL2x8_`, `_AR2020MX4_VB1940X4_`,
`_SDV11NM1x2_SHW3Gx4_`. Прежде был зашит `_YUV_` — по имени он выглядит
«тем самым», потому что камера отдаёт YUV422, — и с ним камера
`SG2-AR0233C-5200-G2A` **не работает**: на всех восьми портах
`sensor_probe camera sgx-yuv-gmsl2-N detect error`, `/dev/video*` создаются,
но поток пустой. Проверено на живой плате 2026-09-11: с `_GMSL2x8_` та же
камера опознаётся и даёт живое видео.

Пакеты расходятся по существу: `Version.md` 20260317 против 20251217 у YUV;
разное `/boot/Image` при одинаковом размере; I²C-адреса камер `0x20..0x23`
против `0x1a..0x1d`; `sgx-yuv-gmsl2.ko` принимает `GMSLMODE_0=`/`GMSLMODE_1=`
(в YUV режим жёстко 6G); для AR0233 `trig_pin=0x00020007` против
`0xffff0007`; есть `pwm-gpio.ko`, `sgcam-gmsl2.ko` и генератор оверлея.
Имя файла DTB-оверлея у обоих **одно и то же**
(`tegra234-camera-yuv-gmsl2x8-overlay.dtbo`), поэтому отличить пакеты по
`extlinux.conf` нельзя. Не возвращай `_YUV_`. Разбор перенесён сюда из
шапки шага `02` станции прошивки (`nvidia-jetpack`), удалённого вместе
с камерами базового образа.

Ветки под JetPack 6.2.1 (L4T 36.4.4) и 7.2.1 в репозитории Sensing есть;
переход на них — отдельная задача: вместе с пакетом меняются оверлей камер
NVIDIA и все закрепления `NVISPPG_*` в `install.sh`.

## Запуск камер: без него кадров нет

Модули ядро грузит само, по дереву устройств, — **без параметров**. Замер
на плате 2026-09-14, образ без шага 8: `/dev/video0..7` на месте,
`max96712_probe: probe success` на обоих дешериализаторах, и при этом на
всех восьми портах `sensor_probe … detect error`, `link:0x02`, а кадры —
одна и та же заглушка по 24 КБ. Модуль получил `GMSLMODE=0,0,0,0`, то есть
GMSL1, а камеры — GMSL2. Узлы есть, картинки нет, и снаружи это выглядит
исправным.

Вендор доводит это интерактивно в `quick_bring_up.sh`. Расширение делает
то же самое без вопросов:

| Что | Чем | Когда применяется |
|---|---|---|
| режим линка (`GMSLMODE`) | `/etc/modprobe.d/bisquite-sensing-gmsl2.conf` | при загрузке модуля — после правки перезагрузка |
| профиль камеры (`v4l2-ctl -c sensor_mode=…`) | правило udev → `bisquite-sensing-camera@videoN.service` | на появление каждого узла, в том числе после `rmmod`/`modprobe` |
| частоты VI/ISP/NVCSI/EMC на максимум (`boost_clock.sh`) | `bisquite-sensing-clock.service` | на каждой загрузке |

**Номер порта знать не нужно** — прежний довод «порт известен только на
месте» к запуску не относится. Профиль ставится на все узлы драйвера:
на пустом порту `v4l2-ctl` проходит без вреда (rc=0), а узлы чужих
драйверов (USB-камеры) скрипт опознаёт по `Card type` и пропускает.
Модель камеры — параметр: на роботах одного профиля она одна.

С шагом 8, та же плата после перезагрузки: порт камеры даёт `link:0xc8`
без `detect error`, 10 разных кадров по ~217 КБ, аппаратная запись H.265
1080p с камеры через `nvv4l2h265enc`.

**Поменять на работающей машине:**

```bash
# профиль и частоты: проверка значения, запись, перезапуск юнитов (хук)
sudo bisquite-conf set sensing-camera SENSING_CAMERA_CONTROLS=sensor_mode=1,trig_mode=0,trig_pin=0x00020007
sudo bisquite-conf set sensing-camera SENSING_BOOST_CLOCK=0
sudoedit /etc/modprobe.d/bisquite-sensing-gmsl2.conf # режим линка — не ручка, модуль
sudo reboot
```

**Найти, на каком порту камера** (для диагностики, работе не нужно):
рабочий порт — тот, где **нет** строки `sensor_probe ... detect error`,
а `dser_link_check link:` даёт `0xc8`, а не `0x02`. У нас камера из
кабеля CN2 оказалась на `/dev/video6`, а не на ожидаемом `/dev/video5`.
Проверка без X: `gst-launch-1.0 v4l2src device=/dev/videoN num-buffers=10
! jpegenc ! multifilesink location=/tmp/f_%02d.jpg` — живая камера даёт
разные хеши, пустой порт одинаковые файлы.

## Переменные окружения

| Переменная | Умолчание | Что делает |
|---|---|---|
| `SENSING_CAMERA_PKG_REL` | `Jetson AGX Orin Devkit/SG8A-AGON-G2Y-A1/JetPack6.2/SG8A_AGON_G2Y_A1_AGX_Orin_GMSL2x8_JP6.2_L4TR36.4.3` | путь к пакету драйверов внутри клона Sensing |
| `SENSING_GMSLMODE` | `1,1,1,1,1,1,1,1` | режим линка по портам 0–7: `0`=GMSL1, `1`=GMSL2 6 Гбит/с, `2`=GMSL2 3 Гбит/с |
| `SENSING_CAMERA_CONTROLS` | `sensor_mode=1,trig_mode=0,trig_pin=0x00020007` | профиль камеры; умолчание — пункт 3 меню вендора, `SG2-AR0233-5200-G-Hxxx`. Другая модель — строка из `quick_bring_up.sh` для её номера |
| `SENSING_BOOST_CLOCK` | `1` | `0` — не фиксировать частоты SoC на максимуме (меньше потребление, вендор так не делает) |

Неверный формат любого из трёх — отказ на сборке, а не молча
неработающие камеры.

## Проверено

Ручной прогон той же последовательности — живая плата, JetPack 6.2,
L4T 36.4.3, 2026-09-11: живое видео 1920×1080 UYVY с `/dev/video6`,
`root=PARTUUID` пережил и заливку, и наложение тестового слоя через
`virt-customize`.

Само расширение (файловые операции + `virt-customize`, без реальной платы)
на момент написания не прогонялось до конца пайплайна `bs image build` —
см. `docs/plans/2026-09-11-jetson-image-pipeline.md` в основном
репозитории.
