# cloud-growroot

Включает модули cloud-init `growpart` и `resizefs`, без которых корень не
растёт до размера носителя.

## Зачем

**Отказ тихий.** cloud-init отрабатывает успешно и рапортует `SUCCESS`,
потому что со своей точки зрения делает всё, что ему поручено: модулей,
читающих `growpart:` и `resize_rootfs:` из seed, просто нет в списке
запускаемых.

Замер 2026-09-03, Raspberry Pi OS Trixie на карте 58 ГБ. Корень остался
11.5 ГБ при 46 ГБ свободного места:

```
sdb2  start 1064960    size 24100864   ← корень, 11.5 ГБ
                       ...46 ГБ свободно...
sdb3  start 121331712  size 204800     ← cidata, у самого конца
```

**Причина не в пакетах.** В образе стоят `cloud-init`, `cloud-guest-utils`
и `e2fsprogs`, бинарники `/usr/bin/growpart` и `/sbin/resize2fs` на месте.
Дело в том, что список `cloud_init_modules` в `/etc/cloud/cloud.cfg` у Pi OS
их не содержит:

```yaml
cloud_init_modules:
  - seed_random
  - bootcmd
  - write_files
  - disk_setup      # ← growpart и resizefs должны быть здесь, до disk_setup
  - mounts
  ...
```

Своего механизма у образа тоже нет: `raspberrypi-sys-mods/firstboot`
и `resize2fs_once` в нём отсутствуют — конкурента у cloud-init не будет.

## Кому нужно

| Образ | Нужно |
|---|---|
| Raspberry Pi OS | **да** — модулей в списке нет |
| Ubuntu Server / cloud | нет — модули в каноническом `cloud.cfg` уже есть |

На образе, где модули уже включены, расширение говорит об этом и **ничего
не меняет** — подключать его «на всякий случай» безвредно, но и бессмысленно.

## Подключение

```vmfile
EXTENSION cloud-growroot
```

Параметров нет.

## Что делает

Вписывает `growpart` и `resizefs` в `cloud_init_modules` **самого
`/etc/cloud/cloud.cfg`**, сразу после `write_files` — там же, где они стоят
в каноническом файле Ubuntu, и до `disk_setup`/`mounts`: расширять раздел
надо раньше, чем на него что-то смонтируют.

Прежний файл сохраняется как `/etc/cloud/cloud.cfg.before-growroot`.

**Почему не файлом в `cloud.cfg.d`.** `util.read_conf_d` сливает фрагменты
через `mergemanydict`, а тот списки **не склеивает**: побеждает целиком тот,
что старше по приоритету. Фрагмент с `cloud_init_modules: [growpart, resizefs]`
заменил бы весь список и унёс бы `users_groups`, `ssh` и `set_passwords` —
карта пришла бы без пользователя и без ключей. Лечение оказалось бы хуже
болезни.

**Отступ берётся у строки-якоря, а не пишется константой.** С жёстко
вписанным пробелом получается смесь одно- и двухпробельных элементов одного
блока, а это невалидный YAML: `cloud.cfg` перестаёт разбираться целиком.
Проверено парсером — первая редакция скрипта ломала файл именно так.

## Отказы

**Нет `/etc/cloud/cloud.cfg`** — cloud-init не установлен; без него ни корень
не вырастет, ни seed не прочитается.

**Нет `growpart` или `resize2fs`** — отказ, а не предупреждение: включённый
модуль без своей утилиты промолчит уже на устройстве, а это ровно тот исход,
который расширение и чинит. Сообщение называет пакеты (`cloud-guest-utils`,
`e2fsprogs`).

**Не нашёлся якорь `write_files`** — список устроен иначе, чем ожидалось.
Расширение не угадывает место вставки: порядок модулей несущий.

## Ограничения

`phase: build`, то есть архитектуры хоста и образа обязаны совпасть. Сама
правка конфигурации архитектуры не касается; ограничение вносит форма
расширения — см. открытый вопрос про расширения без кода в спеке.

**Корень вырастет до начала раздела `cidata`, а не до конца носителя.**
Писалка создаёт seed-раздел в конце диска, и между ним и корнем остаётся
всё свободное место — на практике это почти вся карта, но «вырос не до
самого конца» надо понимать заранее, иначе выглядит недоработкой.

## Проверка

На собранном образе:

```console
$ virt-cat -a образ.qcow2 /etc/cloud/cloud.cfg | grep -A6 cloud_init_modules
```

На устройстве после первой загрузки:

```console
$ lsblk /dev/mmcblk0
$ df -h /
$ grep -i growpart /var/log/cloud-init.log
```
