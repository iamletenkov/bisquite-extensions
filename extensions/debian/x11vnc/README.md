# x11vnc

VNC-доступ к рабочему столу X11 для пользователя, созданного cloud-init.
Сервер поднимается системным юнитом-шаблоном `x11vnc@<пользователь>.service`
и по умолчанию слушает только петлю.

## Манифест

| Поле | Значение |
|---|---|
| `phase` | `[build, firstboot]` |
| `provides` | `remote-desktop` |
| `requires` | `x11-server`, `display-manager` |
| `conflicts` | — |

`build` — `install.sh` ставит пакеты, кладёт юниты и файл параметров;
`firstboot` — `configure.sh` включает `x11vnc@<пользователь>.service`, а имя
пользователя приходит из cloud-init уже на устройстве.

Требование родовое — «любой X-сервер, любой дисплей-менеджер», — и это
верно: путь к X authority в юните не зашит, а ищется в рантайме, а он разный
под LightDM и GDM и зависит от конфига, а не от имени пакета. Различать
в манифесте «какой именно менеджер» значило бы зафиксировать ось, которая
ответа не определяет.

`conflicts` с `vino-vnc` **не объявлен** намеренно — разбор в README
`vino-vnc`, раздел «Соседство с x11vnc»: мешают друг другу не расширения,
а их умолчания (оба берут порт 5900), и разводится это параметром.

## Порядок в VMFILE — несущий, и строк в нём три

```vmfile
EXTENSION yq
EXTENSION xfce4
EXTENSION x11vnc X11VNC_PORT=5901
```

1. **`yq` — выше.** `configure.sh` начинает с `command -v yq` и при его
   отсутствии выходит кодом 1, то есть на первой загрузке сервер не
   включится вовсе. Расширение `x11vnc` само `yq` **не ставит**; ставит его
   отдельное расширение `yq` (и нужен именно mikefarah/yq — см. его README).
   В `requires` манифеста `yq` при этом не объявлен, хотя способность такая
   есть и валидатор её принял бы: порядок держится этой строкой VMFILE,
   а не манифестом.
2. **Десктоп — выше.** Он даёт `x11-server` и `display-manager`
   (`gnome`, `xfce4` или `lxde`). Топологической сортировки у резолвера нет:
   `requires` печатается, но порядок держится этой строкой.

## Параметры сборки

Задаются переменными окружения. В инструкции `EXTENSION` они пишутся
`КЛЮЧ=ЗНАЧЕНИЕ` и уезжают в `install.sh` как есть:

```vmfile
EXTENSION x11vnc X11VNC_PORT=5901 X11VNC_PASSWORD=секрет
```

| Переменная | Умолчание | Что делает |
|---|---|---|
| `X11VNC_PORT` | `5900` | порт RFB (`-rfbport`) |
| `X11VNC_DISPLAY` | `:0` | дисплей X (`-display`) |
| `X11VNC_PASSWORD` | пусто | пароль; без него сервер поднимается с `-nopw` |
| `X11VNC_LISTEN` | `localhost` | `localhost` — только петля (`-localhost`), **любое другое значение** — все интерфейсы |

`install.sh` кладёт первые три в `/etc/default/bisquite-x11vnc`, юнит читает
оттуда. Пароль туда не пишется: `x11vnc -storepasswd` кладёт его
в `/etc/x11vnc/passwd` в собственном формате `-rfbauth`, а в файл окружения
уезжает только путь (`X11VNC_PASSFILE`).

**`X11VNC_LISTEN` — переключатель, а не адрес.** Обёртка сравнивает его ровно
со строкой `localhost` и либо добавляет `-localhost`, либо не добавляет
ничего. Поэтому `all`, `0.0.0.0` и `yes` означают одно и то же — «все
интерфейсы», — а привязать сервер к одному конкретному адресу этим
параметром нельзя.

Значение с пробелами берётся в кавычки — аргумент разбирается `shlex`,
и кавычки снимаются до попадания в окружение:

```vmfile
EXTENSION x11vnc X11VNC_PASSWORD="two words"
```

**Умолчание `localhost` — смена поведения.** Раньше сервер слушал все
интерфейсы и всегда без пароля, а compose-примеры ставят `firewall: false`:
рабочий стол оказывался открыт всей сети из одной строки VMFILE, которую
никто не писал специально. Позиция проекта — только петля, доступ через
SSH-туннель:

```bash
ssh -L 5900:localhost:5900 пользователь@адрес
```

## Параметры времени выполнения

Параметры живут в **`/etc/default/bisquite-x11vnc`** — это `EnvironmentFile`
юнита `x11vnc@.service`, а не копия сборочных значений. Менять их на живой
машине можно и пересобирать образ для этого не нужно.

```console
$ cat /etc/default/bisquite-x11vnc
X11VNC_PORT=5900
X11VNC_DISPLAY=:0
X11VNC_LISTEN=localhost
```

Переключить прослушивание с петли на все интерфейсы:

```bash
# 1. поменять значение (любое, кроме localhost, означает «все интерфейсы»)
sudo sed -i 's/^X11VNC_LISTEN=.*/X11VNC_LISTEN=all/' /etc/default/bisquite-x11vnc

# 2. задать пароль, если его ещё нет, — без него сервер поднимается с -nopw
sudo install -d -m 0755 /etc/x11vnc
sudo x11vnc -storepasswd 'пароль' /etc/x11vnc/passwd
grep -q X11VNC_PASSFILE /etc/default/bisquite-x11vnc || \
  echo 'X11VNC_PASSFILE=/etc/x11vnc/passwd' | sudo tee -a /etc/default/bisquite-x11vnc

# 3. перезапустить сервер того пользователя, для которого он включён
systemctl list-units 'x11vnc@*'                  # узнать имя экземпляра
sudo systemctl restart x11vnc@<пользователь>.service

# 4. убедиться, что слушает то, что ожидалось
ss -ltnp | grep 5900
```

Вернуть обратно — то же самое со значением `localhost`. `daemon-reload`
не нужен: юнит не менялся, менялся `EnvironmentFile`, который читается при
каждом запуске. А вот **`configure-x11vnc.service` перезапускать бесполезно**:
он только находит пользователя и включает экземпляр, параметров не читает.

### Что именно произойдёт при `X11VNC_LISTEN=all`

Сказать это прямо дешевле, чем узнать потом:

- **рабочий стол становится доступен всем, кто дотянулся до порта** — уже
  открытой сессии, с правами вошедшего пользователя, включая его терминалы
  и сохранённые пароли в браузере;
- **трафик не шифруется.** RFB открытым текстом: нажатия клавиш (а значит,
  и пароль `sudo`) идут по сети как есть;
- **пароль VNC слабый по устройству протокола.** Аутентификация RFB (тип 2)
  кладёт в ключ DES ровно восемь байт; девятый символ и дальше
  отбрасываются, перебор по такому ключу дёшев;
- **следа не останется.** Подключение не пишется ни в `wtmp`, ни в журнал
  сессии — только строка в journal самого `x11vnc@`;
- **compose-примеры ставят `firewall: false`**, то есть межсетевого экрана
  перед этим портом может не быть вовсе.

Поэтому штатный путь — оставить `localhost` и ходить SSH-туннелем: так
шифрование и аутентификацию даёт SSH, а VNC остаётся локальным сервисом.
Открывать в сеть осмысленно в изолированном сегменте и с паролем.

## Чего расширение не делает

- **не поднимает десктоп и не выключает Wayland** — это работа десктопного
  расширения (`gnome` пишет `WaylandEnable=false`);
- **не открывает порт в межсетевом экране** и не настраивает туннель;
- **не ставит `yq`**, хотя без него не работает первая загрузка (см. выше);
- **не шифрует трафик** — ни `-ssl`, ни `stunnel` здесь нет.

**Каталог `/opt/vmsetup/x11vnc` обязан остаться в образе.** Оба юнита зовут
скрипты по этому пути в рантайме (`configure.sh` и `run-x11vnc.sh`), а не
копируют их куда-то «к себе». Инструкция `EXTENSION` кладёт каталог именно
туда, так что штатным путём это само собой; но слой, который вычистит
`/opt/vmsetup`, сломает VNC — причём не на сборке, а на первой загрузке.
По той же причине `install.sh` ищет свои файлы по абсолютному
`/opt/vmsetup/x11vnc/...`: `COPY_IN` в другой каталог он не поддерживает и
отказывает на `run-x11vnc.sh`.

**Файл пароля `/etc/x11vnc/passwd` создаётся с правами `0644`** — его может
прочитать любой локальный пользователь. Формат `-rfbauth` не хеш, а
обратимо зашифрованный пароль, так что считать его секретом от локальных
учёток нельзя.

## Что делает

**Сборка** (`install.sh`)

- ставит `x11vnc`, `xauth`, `x11-utils`;
- кладёт `/etc/systemd/system/x11vnc@.service`
  и `/etc/systemd/system/configure-x11vnc.service`;
- пишет `/etc/default/bisquite-x11vnc` и, если задан пароль,
  `/etc/x11vnc/passwd`;
- включает `configure-x11vnc.service`;
- предупреждает, если `X11VNC_LISTEN` не `localhost`, а пароль не задан.

`xauth` и `x11-utils` ставятся **явно**: обёртке нужен `xdpyinfo`, а у пакета
`x11vnc` он лишь в `Recommends`. Раньше они приезжали только потому, что
десктопное расширение ставило `xorg`, — то есть работа зависела от порядка
слоёв, а не от объявленных зависимостей.

**Первая загрузка** (`configure.sh`, юнит `configure-x11vnc.service`)

- отказывает сразу, если нет `yq` или `get_cloud_user.sh`;
- ждёт пользователя cloud-init — до 120 секунд, 40 попыток по 3 с;
- включает и запускает `x11vnc@<пользователь>.service`; **отказ запуска —
  это отказ юнита** (код 1 и строка в журнале), а не тишина: раньше обе
  команды глушились, и немой цикл рестарта выглядел как успех.

Юнит ждёт пользователя **циклом**, а не упорядочиванием: в отличие
от `configure-vino-vnc.service` он не стоит `After=cloud-final.service`,
а висит на `graphical.target` после дисплей-менеджера. Практически это
означает, что запас по времени — те самые 120 секунд, и на очень медленном
cloud-init их может не хватить; в журнале это видно строкой «Timeout waiting
for cloud-init user».

Сам сервер (`x11vnc@.service`) перед запуском ждёт сокет X до 60 секунд
(30 попыток по 2 с), а при падении перезапускается через 5 секунд
(`Restart=on-failure`). Аргументы сервера собирает обёртка:
`-forever -loop -noxdamage -repeat -shared`, плюс порт, дисплей, authority
и либо `-localhost`, либо ничего, и либо `-rfbauth`, либо `-nopw`.

## Как находится X authority

Путь к authority **не зашит в юните**, а ищется в рантайме обёрткой
`run-x11vnc.sh`. Прежний хардкод

```
-auth /var/run/lightdm/%i/:0
```

не работал **ни под одним** дисплей-менеджером. Это склейка двух разных схем
LightDM (проверено по исходникам, версии 1.2–1.32 — одинаково):

- `src/x-server-local.c` пишет `<run-dir>/**root**/:0` — authority самого
  X-сервера, владелец root, права 0600, пользователю недоступен. Отсюда
  и взялось имя файла `:0`;
- `src/session.c` даёт пользователю `~/.Xauthority` (умолчание) либо
  `<run-dir>/<user>/xauthority` при `user-authority-in-system-dir=true`.

Под GDM ≥ 42 файл лежит в третьем месте — `/run/user/<uid>/gdm/Xauthority`
(`gdm/daemon/gdm-x-session.c`).

Обёртка перебирает кандидатов в порядке убывания надёжности и берёт первого,
на котором сработал `xdpyinfo`:

1. `~/.Xauthority` пользователя (LightDM, `session.c`);
2. `/run/user/<uid>/gdm/Xauthority` (GDM ≥ 42);
3. `/run/lightdm/<user>/xauthority` (LightDM при
   `user-authority-in-system-dir=true`);
4. значение `-auth` из командной строки живого `Xorg` (читается
   из `/proc/<pid>/cmdline`) — тот, кто запустил сервер, знает путь точно;
5. legacy-раскладка GDM `/run/gdm3/auth-for-<user>-*/database` — последней,
   на современных сборках её нет.

Перед этим списком обёртка пробует `$XAUTHORITY`, если он задан, — но
в окружении системного юнита его нет, поэтому нумерация выше и нумерация
в замерах ниже совпадают.

Не подошёл ни один — **громкий отказ с перечислением всех проверенных путей**
и пометкой, какие из них существуют. Раньше на этом месте был немой цикл
рестарта каждые 5 секунд.

**`x11vnc -auth guess` не годится.** Его встроенный скрипт FINDDISPLAY
перебирает `~/.Xauthority`, `/tmp/.gdm*`, `/tmp/.Xauth*` и глобы
`/var/run/gdm*/auth-for-*/database` и `auth-cookie-*` — пути GDM ≥ 42 там
нет, а `auth-for-*` это legacy-раскладка. Плюс `man x11vnc` предупреждает,
что FINDDISPLAY зависает навсегда, если гритер держит X-сервер.

## Wayland

`x11vnc` обслуживает X11 и на Wayland-сессии бесполезен. Обёртка спрашивает
у `loginctl` тип сессии и отказывает внятно.

Проверять наличие сокета `/tmp/.X11-unix/X0` для этого **нельзя**: под Wayland
его создаёт mutter для Xwayland, он там есть. Собственная защита `x11vnc`
тоже не сработает — она смотрит на `$WAYLAND_DISPLAY`, которого в окружении
системного юнита нет.

Xorg включает расширение рабочего стола: `gnome` пишет `WaylandEnable=false`.
Это несущая связь между двумя расширениями, и в манифестах она не выражается.

## Подключение в VMFILE

Основной способ:

```vmfile
EXTENSION yq
EXTENSION gnome
EXTENSION x11vnc X11VNC_PORT=5901
```

Прежняя запись продолжает работать; параметры в ней задаются той же строкой,
потому что `RUN_COMMAND` отдаёт её шеллу гостя целиком:

```vmfile
COPY_IN <чекаут>/extensions/debian/x11vnc:/opt/vmsetup/
RUN_COMMAND chmod +x /opt/vmsetup/x11vnc/*.sh
RUN_COMMAND X11VNC_PORT=5901 /opt/vmsetup/x11vnc/install.sh
```

`<чекаут>` — путь до чекаута этого репозитория **относительно каталога
VMFILE**; в примерах основного репозитория это `../../../../bisquite-extensions`,
и глубина зависит от того, насколько глубоко лежит сам VMFILE.

Целевой каталог в `COPY_IN` обязан быть `/opt/vmsetup/`: юниты и `install.sh`
знают этот путь (см. «Чего расширение не делает»).

## Проверка

На собранном образе:

```console
$ virt-cat -a образ.qcow2 /etc/default/bisquite-x11vnc
$ virt-ls -a образ.qcow2 /etc/systemd/system | grep x11vnc
```

На машине после первой загрузки:

```console
$ systemctl status configure-x11vnc.service
$ systemctl list-units 'x11vnc@*'
$ journalctl -u 'x11vnc@*' -b | tail -30     # строка «authority: …»
$ ss -ltnp | grep 5900
```

Ожидаемое при умолчаниях — `127.0.0.1:5900`; при `X11VNC_LISTEN=all` —
`0.0.0.0:5900`.
