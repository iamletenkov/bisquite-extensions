# sensing-gmsl2-camera

Драйверы камер Sensing GMSL2 для **Jetson AGX Orin Developer Kit** (модуль
p3701-0000, носитель p3737-0000) с адаптером **SG8A-AGON-G2Y-A1**: замена
ядра, модули `.ko`, DTB-оверлей, новая запись в загрузочном меню.

## Манифест

| Поле | Значение |
|---|---|
| `phase` | `build` |
| `arch` | `arm64` |
| `provides` | `gmsl2-camera` |
| `requires` | пусто |
| `conflicts` | пусто |

## Зачем это слой, а не часть базового образа

Камеры — свойство конкретного адаптера на конкретных роботах, а не платы
Jetson вообще. Базовый образ (`jetson-orin-base`) остаётся общим для всего
флота; этот слой ложится только на VMFILE тех машин, где адаптер физически
установлен.

## Что делает

1. Проверяет, что это именно AGX Orin с адаптером `p3737-0000+p3701-0000` —
   по наличию `/boot/dtb/kernel_tegra234-p3737-0000+p3701-0000-nv.dtb` в
   уже собранном базовом образе. `/proc/device-tree` для этого не годится:
   внутри `virt-customize` гость не загружен, это chroot поверх файловой
   системы, а не работающая Tegra.
2. Клонирует `SENSING-Technology/nvidia-jetson-camera-drivers` и берёт
   пакет `..._GMSL2x8_...` (не `_YUV_` — с ним камера `SG2-AR0233C-5200-G2A`
   не работает, `sensor_probe detect error` на всех восьми портах; разбор —
   в `nvidia-jetpack/scripts/02-fetch-camera-drivers.sh`).
3. Бэкапит штатное ядро в `/boot/Image.backup` (идемпотентно — `cp -n`),
   заменяет `/boot/Image` на ядро Sensing.
4. Кладёт `.ko`-модули в `/lib/modules/5.15.148-tegra/updates/...`, снимает
   штатный `max96712.ko`.
5. Копирует DTB-оверлей в `/boot/`.
6. Кладёт весь пакет драйверов в `/opt/sensing` — для ручного
   `quick_bring_up.sh` на устройстве (см. ниже, почему не автоматизирован).
7. Правит `/boot/extlinux/extlinux.conf`: добавляет запись `JetsonIO`
   с оверлеем и делает её умолчанием, добавляет резервную запись `backup`
   на `/boot/Image.backup` — с **тем же** `root=`, что и у исходной записи
   (вендор в своём примере даёт `backup` без `root=` вовсе — такая запись
   не загрузится). Существующий `root=PARTUUID=...` не трогает: он
   переносится дословно в обе новые записи.

## Почему `quick_bring_up.sh` не вызывается расширением

Он спрашивает модель камеры и **номер порта**, а номер порта — не то, что
можно вычислить заранее: он определяется по факту на конкретной сборке
адаптера. У нас на одной и той же плате камера из кабеля CN2 оказалась на
`/dev/video6`, а не на ожидаемом `/dev/video5` — нашлась только по
отсутствию `sensor_probe ... detect error` в `dmesg`. Автоматизировать этот
шаг на сборке значило бы дать ложное чувство готовности: образ считался бы
собранным с камерами, а по факту без проверки на живом устройстве это
неизвестно.

**После записи образа на устройство, вручную:**

```bash
cd /opt/sensing
sudo ./quick_bring_up.sh
# на вопросы про GMSL1 и GMSL2 3Gbps — Enter (камеры в режиме 6G по умолчанию)
# модель — пункт 3 (SG2-AR0233-5200-G-Hxxx)
# порт — искать по dmesg, см. ниже
```

Как искать порт: рабочий — тот, где **нет** строки `sensor_probe ...
detect error` и где `dser_link_check link:` даёт ненулевую маску. Второй
признак — `v4l2-ctl -d /dev/videoN --get-fmt-video` показывает родное
разрешение камеры (1280×960 для AR0233) вместо дефолтного 1280×720
у пустого порта.

## Проверено

Ручной прогон той же последовательности — живая плата, JetPack 6.2,
L4T 36.4.3, 2026-09-11: живое видео 1920×1080 UYVY с `/dev/video6`,
`root=PARTUUID` пережил и заливку, и наложение тестового слоя через
`virt-customize`.

Само расширение (файловые операции + `virt-customize`, без реальной платы)
на момент написания не прогонялось до конца пайплайна `bs image build` —
см. `docs/plans/2026-09-11-jetson-image-pipeline.md` в основном
репозитории.
